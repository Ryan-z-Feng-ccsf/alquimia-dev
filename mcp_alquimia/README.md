# Alquimia MCP server

The local stdio MCP server controls persistent native processes linked to an existing Alquimia installation. Each simulation session keeps its own engine state across requests.

The server's cases are defined in code (`src/mcp_alquimia/cases/registry.py`), one per chemistry system, each naming its PFLOTRAN and/or CrunchFlow input under `benchmarks/batch_chem`. The physical condition (density, porosity, temperature, pressure, volume, saturation) and time stepping are kept separate from the inputs and are the same defaults for every case: the physical defaults are the defaults of `setup`'s `request` schema, and `list_cases` sends the time-stepping defaults once, followed by each case's engines and description. Each case's database files are read from its input file. The `*.cfg` files remain for the original batch driver and are not read by the server.

A session runs one engine: `setup(case, engine)` takes an engine `list_cases` shows the case under. To compare engines, run one session per engine with the same request and time configuration. `setup` accepts an optional `request` object that overrides the physical settings and, through `request.chemistry`, initial concentrations, pH, gas pressures, mineral volume fractions and surface areas, and mineral rate constants. `get_chemistry(case, engine)` lists that input's editable names and current values. Chemistry values use engine-independent units (mol/L water, Alquimia's state unit; pH, bar, m^2/m^3 bulk, mol/m^2/s) and are converted to each engine's input units (CrunchFlow's mol/kg with the session's water density), so one request means the same on every engine and matches the concentrations the simulation reports. Changes are written only into the session's staged copy of the input, using a lossless parse that rewrites only the edited tokens; a constraint's type (e.g. charge balance) is never changed. Each case supports configurable step count and timestep, and pytest coverage against the original batch driver. Responses are compact JSON text for an LLM client: state is keyed by species and mineral name, values keep 6 significant digits (pH 3 decimals), and `setup` sends the units of every response once. Session artifacts keep the full-precision engine output. It reuses precompiled engines; compilation is never part of simulation requests.

The `mcp-alquimia` command starts the MCP server. Use `list_cases`, optionally `get_chemistry(case, engine)`, then `setup(case, engine)` to obtain a session ID, `initialize(session_id)`, `react(session_id)`, which runs `max_steps` steps of `dt` seconds in one engine request (an optional `time_config` overrides both, starting from the defaults), `get_results(session_id)`, and `close(session_id)`. The server closes remaining sessions on disconnect.

`search_docs(query, collection?, limit?)` and `read_doc(doc_id)` search the PFLOTRAN and CrunchFlow manuals and the Alquimia known issues (`collection` is `pflotran`, `crunchflow` or `alquimia`). They read a prebuilt SQLite FTS5 index (default `build/mcp_alquimia/manual_index.sqlite`, override with `--manual-index`), which the container image builds from `docs/`. See [docs/README.md](docs/README.md) for the sources and how to rebuild the index.

Inputs, logs, operation records, results, and failure diagnostics are retained under `~/.alquimia/runs/<session_id>/` by default (override with `--run-root`). Native failures end the affected session; start a new session to retry. Invalid arguments and lifecycle-order errors leave the session usable.

Any case can also be run without MCP through `uv run --project mcp_alquimia python mcp_alquimia/scripts/run_batch_chem_case.py --case <name> --engine <engine> --run-dir <new dir>` (optionally `--request '<json>'` for setup overrides, and `--max-steps`/`--dt`). [Container packaging](containers/README.md) builds a self-contained Linux x86-64 image and runs without host sudo when rootless Docker prerequisites are available; a second launcher runs the published image on a rootful system daemon.
